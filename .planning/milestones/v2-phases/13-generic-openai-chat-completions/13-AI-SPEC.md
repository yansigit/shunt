## 1. System Classification

**System Type:** Deterministic protocol gateway adapter; not an agent/RAG application.

**Description:**
Translate Anthropic Messages requests to a configured Chat Completions upstream and translate checked JSON/SSE output back, preserving supported tools, content, usage and termination without changing existing providers.

**Critical Failure Modes:**
1. Credentials escape the configured destination or appear in diagnostics.
2. An ambiguous post-send failure causes generation replay.
3. Malformed or incomplete output becomes false success.
4. Tool identities or arguments are silently fabricated or repaired.
5. Unbounded state or incomplete cancellation leaks resources.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Developer tooling — LLM API protocol gateway infrastructure.

**User Population:** CLI/agentic coding clients (Codex and Anthropic-protocol clients) whose operators configure OpenAI Chat Completions-compatible upstreams; no end-user-facing content generation happens here.

**Stakes Level:** High — duplicated tool execution, credential leakage, and false-completion streams directly break downstream agent workflows (and can bill or side-effect twice), though the gateway itself stores no regulated user data.

**Output Consequence:** Every relayed byte is consumed as authoritative protocol output by a client agent: a synthesized terminal ends a run as success, a re-dispatched request can execute a tool twice, and a credential-bearing redirect hands an API key to an unapproved destination. Correctness is judged by wire conformance (CHAT-01–09), not output quality.

### What Domain Experts Evaluate Against

> This is a deterministic protocol gateway, not a generative application. "Domain experts" are gateway/protocol practitioners; approved semantics come from the phase decisions (13-CONTEXT D-01–D-10), the repo contract (REQUIREMENTS CHAT-01–09, SAFE-01–07, PRES-03/04), and PITFALLS research — not model-output quality judgments, legal research, or live spec verification.

1. **Tool-call identity and pairing integrity**
   Good: Declared tools, tool choice, parallel calls, and paired results arrive at the upstream with original names, IDs, and adjacency; deltas keyed by index then id assemble exactly once; orphan, duplicate, missing-identity, and incomplete-argument input is rejected with a typed 400 (D-05, CHAT-04, SAFE-06).
   Bad: Results are synthesized or repaired, IDs regenerated, calls dropped while results remain (the OpenCodex #1383 class of bug), or arguments guessed mid-stream.
   Stakes: Critical — Source: SAFE-06, PITFALLS "Breaking tool-call/result pairing".
2. **Replay and re-dispatch discipline**
   Good: Generation requests pin ConnectOnly retry safety; no retry or failover occurs after send, client-visible output, or replay-unsafe tool activity (D-09; PRES-03, SAFE-04).
   Bad: A transient-timeout or ambiguous post-send failure triggers redispatch or provider hopping, duplicating output, tool side effects, or billing.
   Stakes: Critical — Source: SAFE-04, PITFALLS "Retry or failover after commitment".
3. **Single trustworthy terminal**
   Good: Exactly one finish/terminal outcome per response in both JSON and SSE modes from one semantic state machine; malformed events, invalid UTF-8, residual bytes, incomplete tools, embedded errors, duplicate terminals, and premature EOF fail closed (D-06/D-07, CHAT-05–07, SAFE-03).
   Bad: EOF is treated as success, a truncated stream ends as a clean stop, or unary mode silently returns HTTP 200 while streaming surfaces a provider error (PITFALLS "Streaming/unary semantic drift").
   Stakes: Critical — Source: SAFE-03, PITFALLS "Treating EOF as success".
4. **Credential and destination routing exactness**
   Good: API keys come only from the configured source; inbound credential slots are stripped; redirects are refused (policy none); credentials reach only the accepted upstream origin and stay out of diagnostics (D-02/D-03, CHAT-02/08, SAFE-05).
   Bad: A configured credential header survives a 3xx to a lookalike host, an API root is silently reinterpreted, or Responses endpoints/fields leak into the Chat request (D-02/D-04).
   Stakes: Critical — Source: SAFE-05, PITFALLS "OAuth token exfiltration" and "Assuming one OpenAI-compatible dialect".
5. **Bounded, ownership-based transport**
   Good: Events, residuals, tool count/arguments, aggregation, and diagnostics all have named tested bounds; read deadlines exist on every read; cancellation drops the owning stream tuple, releasing upstream and admission capacity with no registry (D-08, SAFE-01/02/07).
   Bad: Unbounded buffering of a streaming body, a detached task outliving the request, or a global cancellation registry.
   Stakes: High — Source: SAFE-01/02/07, D-08.

### Known Failure Modes in This Domain

From PITFALLS research and the phase decisions, as they manifest in this adapter:

- **Commitment-boundary violation:** retry/failover classified off the idempotent-helper path re-sends a generation POST after output or tool activity (PITFALLS "Retry or failover after commitment"; D-09 locks ConnectOnly).
- **EOF-as-success:** adopting upstream lenient done-on-empty/EOF-tolerance branches turns truncated streams into clean completions — explicitly not ported from OpenCodex (D-07; Section 3 Pitfall 3).
- **Silent frame loss:** dropping invalid UTF-8, malformed data JSON, or oversized frames instead of failing with one terminal error (PITFALLS "Ignoring malformed or oversized frames").
- **Streaming/unary drift:** the two output modes disagree on tools, usage, finish reason, or embedded provider errors because they bypass the shared machine (D-06/D-07 one-contract rule).
- **Credential escape:** reqwest default redirect-following carries a configured API-key header across hosts on a 3xx (Section 3 Pitfall 1; D-03).

### Common Pitfalls

1. **Relying on reqwest's default redirect policy.** It follows up to 10 hops and
   strips only `Authorization`/`Cookie`-class headers on cross-host redirects — a
   configured `x-api-key` would follow a 3xx. Build the client with
   `Policy::none()` and surface the 3xx (telemetry_ingest.rs:371-376 rationale).
2. **Reusing `RetrySafety::NonIdempotentPost`.** It admits transient-timeout
   retries at retry.rs:171-179 *even after send*; a pre-header failure is not
   necessarily pre-send. Pin `ConnectOnly`; report `AdapterFailure::BeforeHeaders`
   only for genuine pre-send transport failures.
3. **Porting the OpenCodex `openaiChatEofTolerance` branch.** Premature EOF,
   residual bytes, and duplicate `[DONE]`/finish_reason must fail closed (D-07);
   the upstream lenient branch is explicitly not ported.
4. **Guessing tool-delta pairing.** Key deltas by `index` first, then `id`;
   tolerate field provenance across deltas but hard-fail a call reaching the
   terminal without `function.name`, duplicate index/id pairing, or arguments
   over the byte budget (D-05 assembly-boundary correction in PATTERNS).
5. **Buffering the upstream stream.** Preserve streaming semantics — the relay
   is an `unfold` owning stream/decoder/machine/residual; dropping it releases
   upstream + admission capacity (ownership-based cancellation, D-08).

## 4. Implementation Guidance

**Model Configuration:**
Model is passthrough routing data (`route.model` → `route.upstream_model`), not a
gateway-side model choice. Translate the generation controls the Anthropic
ingress actually carries — `max_tokens`, `temperature`, `top_p`, `stop`, `stream` —
into equivalent Chat Completions fields, assembling the outbound body by
whitelist (`out: Map`, insert only translated fields) so Responses-only or
Anthropic-only keys never leak (D-04). Unsupported representations get a 400,
never silent drops. No sampling defaults are invented server-side.

**Core Pattern:**
Two pure boundary functions plus one shared machine:

```rust
// Request: pure, typed-rejection, whitelist assembly (gemini_request.rs shape)
pub fn translate_request(request: &Value) -> Result<Value, AdapterError>;

// Response: ONE machine serves both output modes (D-06/07)
// - JSON mode: machine.final_json_checked(&body) after bounded collect_unary_response
// - SSE mode:  machine.process_chunk_checked per frame; transport_close_checked on EOF
```

Send path: `RetrySafety::ConnectOnly`, TTFB deadline via `upstream_timeout::wait`,
redirect-`Policy::none()` client; local errors use the Anthropic error shape with
`failure: None` (gateway-owned validation failures never re-dispatch; the
Codex-endpoint OpenAI-shape exception does not apply — Chat ingress is
Anthropic-shaped). Streaming relay: `futures_util::stream::unfold` tuple owning
(byte stream, decoder, machine, finished, pending residual), wrapped in
`keepalive::with_pings`; errors emit an Anthropic `error` event, then the stream
terminates. Unary JSON mode copies `collect_unary_response` bounds
(`MAX_CHAT_UNARY_RESPONSE_BYTES`, content-length pre-check, `checked_add`). Named
bounds consts for events, residuals, tool count, arguments, aggregation and
diagnostics; read deadlines everywhere (D-08).

**Tool Use:**
Outbound declarations keep original names/descriptions; supported `tool_choice`
is translated, unsupported choices rejected. Assistant `tool_calls` =
`[{id, type: "function", function: {name, arguments: string}}]`; tool results =
`{role: "tool", tool_call_id, content}`. Inbound results are validated for
identity, uniqueness, and pairing with the pending call — orphan, duplicate,
missing-identity, and incomplete-JSON arguments are `bad_request`; never
repaired or synthesized (D-05). Streaming accumulation keys deltas by `index`
first then `id`; arguments accumulate as raw strings and are parsed **once at
close** (one JSON parse of the complete object). Parallel calls and original
IDs are preserved end-to-end.

**State Management:**
No persisted state. Pure ownership: admission guard moved into the body stream
(`adapters/mod.rs:19-41` pattern); stream/decoder/machine owned by the `unfold`
tuple — dropping the client connection mid-stream drops the tuple and releases
upstream + capacity with no registry or detached task (D-08). No credential
writeback, no new persistence (D-01/D-03).

**Context Window Strategy:**
N/A as model-context management — the gateway never truncates or summarizes
user content. "Window" means transport bounds, all named consts: per-event
bytes, unary response bytes, tool count, tool-argument bytes, residual buffer,
diagnostics, read deadlines (D-08). Long-context conformance verifies behavior
at a boundary, not content rewriting.

## 4b. AI Systems Best Practices

> Template assumes a Python AI framework; adapted for the NONE decision.
> Framework-specific and inapplicable items are marked N/A with rationale —
> no prohibited dependency is invented.

### Structured Outputs with Pydantic

**N/A — no Python, no Pydantic (approved scope).** Equivalent contract in
Rust/serde terms: parse each upstream frame as `serde_json::Value`, then apply
**checked semantic validation** before anything reaches the client — typed
required fields, one trusted terminal (finish/`[DONE]`), UTF-8 completeness,
complete tool objects (name present; arguments parsed once at close as one
JSON value), bounded sizes. Failures are typed protocol errors
(`GeminiSemanticError` pattern), fail-closed, no retry, no repair. Where a
Pydantic stack would "validate or retry" against a model, this contract is
deterministic, so validation failure is a hard protocol error.

### Async-First Design

Everything runs on the existing Tokio runtime; the adapter adds no executor.
The one common mistake to avoid: **blocking or buffering in the streaming
path** (collecting the byte stream, or thread sleeps) — use the `unfold` relay
and reuse `keepalive::with_pings` / `upstream_timeout::wait`. Stream vs. await:
SSE relays incrementally to the client (preserve streaming semantics); unary
JSON mode awaits inside a bounded collect with a hard byte ceiling.

### Prompt Engineering Discipline

Not applicable to prompt *authoring* (the gateway authors no prompts). The
mapping discipline here is **translation fidelity**: system/user/assistant text
maps to Chat roles without reordering or merging; nothing is silently dropped
(D-04). Explicit bounds always set — max-tokens passthrough and named size
consts instead of unbounded behavior.

### Context Window Management

N/A for RAG chunking / summarisation / compaction — deterministic gateway, no
cross-request context retention; conversation context lives entirely in the
client-supplied messages array. The managed resource is transport memory:
bounded event frames, arguments, residual, diagnostics (D-08).

### Cost and Latency Budget

No per-call model cost accrues to the gateway. Latency discipline: TTFB
deadline on the upstream send, keepalive pings during streaming, bounded unary
collection, and **no caching or failover re-dispatch** — generation is
non-idempotent and post-send ambiguity must never trigger retries or fallback
(D-09). Regressions are caught by the conformance harness
(late-timeout/no-fallback test), not by a caching layer.

### Reference Dataset

**Size:** ≥ 12 fixture scenarios (above the 10-example floor; 12 gives room
for success and failure twins). Each scenario is a concrete upstream payload
+ expected client-visible outcome, not an example prompt.

**Composition:**
Required scenarios (success and failure twins; expected result stated as
PASS/FAIL assertion):

1. **Normal unary JSON** — text completion, usage, `finish_reason: stop` →
   PASS: Anthropic response with matching text/usage/`end_turn`.
2. **Normal streaming text** — incremental `delta.content` frames then
   `finish_reason` + `[DONE]` → PASS: incremental relay, exactly one terminal.
3. **Tool-heavy unary** — declared tools, `tool_choice`, parallel assistant
   `tool_calls`, paired `role: "tool"` results → PASS: original IDs/names/
   adjacency preserved outbound; nothing synthesized.
4. **Tool-delta streaming, interleaved** — multiple indexed `delta.tool_calls`
   interleaved with text/reasoning, arguments split across frames → PASS:
   assemble by index-then-id once; single JSON parse of complete arguments at
   close.
5. **Truncation / premature EOF** — stream ends mid tool call or without
   `finish_reason`/`[DONE]` → FAIL-closed: one typed error event, never a
   clean stop; the EOF-tolerance branch does not exist (D-07).
6. **Malformed frames** — invalid UTF-8, non-object `data` JSON, duplicate
   terminal, residual bytes after `[DONE]`, non-array `delta.tool_calls` →
   FAIL-closed: single error and no success terminal; previously relayed valid text cannot be retracted, and malformed tool arguments must never become a dispatchable tool call.
7. **Embedded provider errors** — `finish_reason: "error"`, `payload.error`,
   unary HTTP 200 with error body → FAIL-closed: recognized detail extracted
   (request-id allowlist, redacted) into Anthropic error shape; no silent
   success; unary and streaming agree.
8. **Tool pairing violations (request side)** — orphan tool result, duplicate
   `tool_call_id`, missing identity, incomplete JSON arguments → PASS: typed
   400, never repaired or synthesized (D-05).
9. **Long-context boundary** — request near the message/event bound; oversized
   single event, oversized tool arguments, oversized unary body → PASS: named
   bound enforced with one typed error; no unbounded growth (D-08).
10. **Auth & destination** — configured key source; inbound
    `authorization`/`x-api-key` slots stripped before dispatch; 3xx from
    loopback upstream → PASS: redirect refused (`Policy::none()`), key reaches
    only the configured origin, key never appears in diagnostics/logs/fixture
    output (CHAT-08, SAFE-05; fixtures use synthetic credentials only).
11. **Cancellation** — client drop before headers and mid-stream (text and
    tool-delta modes) → PASS: owning `unfold` tuple dropped, upstream
    connection and admission permit released within a bounded time, no
    registry (D-08, SAFE-07).
12. **Retry discipline / ambiguous post-send** — loopback upstream that hangs
    after receiving the request, plus a request with replay-unsafe tool
    activity and a failing alternate provider configured → PASS: no
    retry/failover after send or output; `BeforeHeaders` reported only for
    genuine pre-send connect failures; `ConnectOnly` pinned (D-09, PRES-03).

**Labeling:**
Expected outcomes are labeled by the protocol conformance engineer directly
from the locked decisions (D-01–D-09) and REQUIREMENTS (CHAT/SAFE/PRES) —
there is no calibration loop because assertions are deterministic. The

## 6. Guardrails

> Guardrail/flywheel split for a deterministic gateway: catastrophic behaviors
> (credential escape, replay after send, false terminal) are enforced as
> **compile-time pinning + fail-closed code paths exercised on every request**
> — the online guardrail *is* the adapter contract itself, verified by
> fixtures, not a bolt-on runtime check. Offline "flywheel" reduces to the
> existing CI suite plus fixture additions when new failure modes are learned.

### Online (Real-Time)

| Guardrail (in-code, always active) | Trigger | Intervention |
|------------------------------------|---------|--------------|
| Redirect refusal | Any 3xx from the upstream (client built with `Policy::none()`) | Block: surface the status as a typed error; no credential ever follows a redirect (D-03) |
| Commitment boundary | Any post-send failure classification attempt | Block: `ConnectOnly` rejects re-dispatch after send/output/replay-unsafe tools; ambiguity resolves to no-retry (D-09) |
| Fail-closed terminal gate | Malformed event, EOF without terminal, duplicate terminal, residual bytes, incomplete tool call, embedded error | Block: exactly one typed gateway error event, stream terminates; no partial success (D-07, SAFE-03) |
| Input validation gate | Orphan/duplicate/unidentified tool results, incomplete arguments, ambiguous API root, unsupported representation | Block: typed 400 before any upstream send (D-02/D-04/D-05) |
| Size/read-deadline bounds | Any event, residual, tool argument, or unary body exceeding its named const; stalled read | Block: one typed error; buffers and reads never grow unbounded (D-08, SAFE-01) |
| Credential redaction | Any diagnostic/log/error path | Block: configured keys and synthetic fixture credentials redacted before emission (SAFE-05, REL-02) |

### Offline (Flywheel)

| Metric | Sampling Strategy | Action on Degradation |
|--------|------------------|----------------------|
| Conformance suite pass rate (`cargo test --all-features --workspace`) | Run on every PR (full workspace) | Block merge; failing scenario becomes a regression fixture |
| New failure-mode capture (protocol bugs found in review/issue triage) | Ad hoc; each learned failure becomes a new fixture scenario in Section 5's dataset | Add pass/fail twin fixture in the same PR as any behavior change (D-11 docs+tests rule) |
| SAFE/CHAT invariant coverage audit | Per-phase review by `gsd-eval-auditor` | Phase gate: scenarios 1–12 above must each be present with both sides labeled |

## 7. Production Monitoring

**Tracing Tool:** Existing gateway observability only (tracing crate /
existing telemetry plumbing already in the repo). **No production monitoring
service is configured by this task.** Third-party platforms (Phoenix,
Langfuse, LangSmith) are not introduced: no new dependencies are permitted,
and the gateway's per-request tracing (request IDs, provider kind, terminal
outcome, redacted failure classification) already exists at the dispatch layer
this adapter plugs into.

**Key Metrics to Track:**
Observed via existing gateway logs/traces only — not wired to any alerting
system by this phase:

1. Upstream status distribution for Chat dispatch (incl. refused redirects).
2. Gateway-owned 400 rate (input-validation gate: tool pairing, API root,
   unsupported representations).
3. Fail-closed terminal rate (truncation / malformed / embedded provider
   errors, by failure class).
4. Pre-send vs. post-send failure classification counts (`BeforeHeaders` and
   other classes; any non-zero post-send retry would be a contract breach).
5. Bounded-resource hits (event/argument/unary byte caps) and cancellation
   releases.

**Alert Thresholds:**
None configured by this task — this phase defines no paging/alerting
integration. Any future operator alerting should key on: sustained 100% of
Chat dispatches failing closed (provider outage), any occurrence of a
post-send re-dispatch (contract breach, investigate immediately), and
credential-redaction violations (critical).

**Smart Sampling Strategy:**
No production interaction sampling is configured by this task (the operator
chooses whether to run this gateway in production and with what observability
stack; the adapter adds none). Within the repo, review sampling is
signal-based instead: PR review and `gsd-eval-auditor` prioritize any change
touching the terminal state machine, tool pairing, credential handling, or
retry classification — the four code regions where a defect converts directly
into the Section 1 critical failure modes. Hands-on Computer/terminal smoke
inspection of the D-10 tracer (isolated `OPENCODEX_HOME`, non-10100 port) is
a supplementary human check at implementation time and is explicitly not
production monitoring.

**Computer execution constraint:** the primary agent performs UI actions; any
Computer subagent must be GPT-6 Astra with explicit high reasoning effort.
On this run Computer rejected Terminal access and blocked the isolated localhost
browser URL. These attempts are blocked, not successful smoke evidence. The
separate five-check shell smoke passed; it does not establish Computer acceptance
or generic Chat behavior before that adapter exists.
