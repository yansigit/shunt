The built-in **`antigravity`** provider reaches Google's **Antigravity** backend over HTTP at
`daily-cloudcode-pa.googleapis.com` — the `daily-` control plane the Antigravity client itself
addresses for both discovery and inference. It speaks the same Code
Assist protocol as the `gemini` provider — shunt translates Anthropic Messages to
`streamGenerateContent?alt=sse` — but it authenticates with an Antigravity subscription
token and identifies itself as `ideType: ANTIGRAVITY` during project discovery.

Antigravity has a second, older transport. `kind = "antigravity_cli"` runs the local `agy` binary
as a subprocess and is **deprecated** — see
[the deprecated `antigravity-cli` transport](/guides/providers/#the-deprecated-antigravity-cli-transport).
This page covers the HTTP provider, which needs none of that machinery.

<Aside type="caution" title="Antigravity's terms">

Google's [Antigravity terms](https://antigravity.google/terms) name this use directly: "using third party software, tools,
or services to access the Service (e.g. using OpenClaw with Antigravity OAuth) is a breach of this
Agreement", and such a breach "may be grounds for suspension or termination of your Antigravity
and/or Gemini CLI accounts". shunt is third-party software using Antigravity OAuth, so routing
through this provider falls squarely under that clause. Whether the subscription is worth that risk
is your own call — nothing here can shield the account.

</Aside>

## Native tool history

Native OAuth responses use opaque `call_antigravity_v2_` tool IDs. Preserve these IDs and the original tool names, arguments, and history order when returning tool results. Legacy `call_gemini_v1_` IDs remain valid for non-native Gemini but are rejected by native Antigravity; start a new conversation when migrating old native history.

The session is derived from the account and canonical opening user turn, so follow-ups keep the same session. Identical openings in the same account share a session. Tags bind the account/session and each call's upstream signature, name, arguments, and conversation-wide ordinal. They are unkeyed context checks, not cryptographic proof of upstream origin: deliberately recomputed tags cannot be detected. Upstream signatures are preserved without synthesis, and no signature cache or signing key is persisted.

## Quick start

Let a coding agent wire it up for you — `shunt add` prints an embedded setup blueprint
(offline and read-only; the agent edits the config, the command never does):

```bash
shunt add upstream antigravity --print | claude
```

Or follow the manual steps below.

## 1. Log in

```bash
shunt login antigravity
```

This runs a Google authorization-code flow using Antigravity's own OAuth client and writes
`~/.shunt/antigravity-auth.json`, which shunt reads and auto-refreshes. The flow asks for five
scopes:

```text
https://www.googleapis.com/auth/cloud-platform
https://www.googleapis.com/auth/userinfo.email
https://www.googleapis.com/auth/userinfo.profile
https://www.googleapis.com/auth/cclog
https://www.googleapis.com/auth/experimentsandconfigs
```

The last two are the reason **a Gemini CLI login cannot be reused here, and vice versa**: a
`~/.gemini/oauth_creds.json` token never carries `cclog` or `experimentsandconfigs`. `google_oauth`
and `antigravity_oauth` are not interchangeable.

Login also resolves your Code Assist project — `loadCodeAssist` first, then `onboardUser` to
provision one for a first-time account — and stores the project id in the credential file. No
discovery sits in front of your first request. If discovery fails, login still saves the token and
retries on the first request.

## 2. Configure the upstream

The provider is built in, so a `[[routes]]` entry naming `provider = "antigravity"` works with no
provider table of your own. Declaring it as an ordered upstream is different: **the Antigravity
kinds have no `[[upstreams]]` preset**, so `provider = "antigravity"` is not available there and you
must set `kind`, `base_url`, and `auth` yourself:

```toml
[[upstreams]]
name = "anthropic"
provider = "anthropic"   # keep Anthropic as the default for unrouted models (e.g. claude-*)

[[upstreams]]
name = "antigravity"
kind = "antigravity"
base_url = "https://daily-cloudcode-pa.googleapis.com"
auth = "antigravity_oauth"
```

Ordered `[[upstreams]]` replace shunt's built-in providers, so an explicit config must also declare
the `anthropic` default it still falls back to (`server.default_provider` defaults to `anthropic`).

The legacy `[providers.antigravity]` table form remains supported — but do not mix `[[upstreams]]`
and `[providers.*]` in one file.

## 3. Route an exact catalog model

Native inference requires fresh account-specific `fetchAvailableModels` evidence for the exact `upstream_model`. The catalog snapshot is bounded and keyed by backend, account fingerprint, and project. A successful cached snapshot remains fresh within its ten-minute TTL; a stale snapshot or failed/cold lookup cannot authorize inference. Authentication and catalog discovery may occur before rejection, but unsupported tuples never reach inference. Catalog discovery refuses redirects; only the configured endpoint may supply admission evidence.

Use an exact Gemini catalog ID. Shunt does not append a suffix, choose a nearby effort, repin a missing model, or forward Claude/GPT catalog entries through this native adapter. A bare ID is not expanded into another model. Catalog membership can change; the following is a configuration example, not a current availability promise:

```toml
[[routes]]
model = "claude-gemini-via-antigravity"
provider = "antigravity"
upstream_model = "gemini-3.8-flash-high"
```

Configured route/provider `effort` takes precedence over the request's `output_config.effort`. An explicit effort must match a suffixed catalog ID. An exact `-tiered` ID carries `low`, `medium`, or `high` in `generationConfig.thinkingConfig.thinkingLevel`, defaulting to `medium` when no effort is supplied. Unknown efforts, including `xhigh` and `max`, are not silently folded. A thinking budget remains a generation control; it no longer guesses a different catalog model.

## Native transport and recovery

Both client modes use `streamGenerateContent?alt=sse`. Streaming relays events incrementally; only non-streaming clients use bounded accumulation. Text, reasoning, ordered tools, usage, finish state, and embedded errors share one checked decoder. Malformed/truncated streams, incomplete tools, and invalid or duplicate terminals fail closed.

An initial `401`, before downstream headers or output, permits one same-account in-memory refresh and one replay with identical project, catalog, session, request ID, and body; only the bearer changes. A second `401`, refresh failure, account change, ambiguous send, or error after headers/output/tools never replays or hops providers. The new recovery path does not write credentials. Existing login/expiry-refresh persistence is unchanged; a legacy refresh-token-derived identity change fails closed. Cancelling either client mode releases the upstream body and admission slot.

Evidence is synthetic, hermetic router/loopback testing dated 2026-09-07, not a live model-availability guarantee. Google AI Studio Web is excluded. No durable signature storage, generalized cache/storage platform, cross-account project reuse, or no-progress cancellation heuristic is added.

## What the adapter carries

The adapter streams assistant **text** and **thinking** as Anthropic SSE, and bridges your client's
**tools** natively: `tool_use` becomes a Gemini `functionCall`, your `tool_result` becomes a
`functionResponse`, and tool declarations and tool choice are translated with it. **System prompts**
become `systemInstruction`. Token usage is Google's reported count — `promptTokenCount` and
`candidatesTokenCount` map to `input_tokens` and `output_tokens`.

**Thinking** follows the request: `thinking.type = "enabled"` sets `thinkingConfig.thinkingBudget` from `budget_tokens` (default `1024`), and `"disabled"` sets it to `0`.

Every request carries `model`, `project`, `userAgent: "antigravity"`, `requestType: "agent"`, a fresh `requestId: "agent-<uuid>"`, and `request.sessionId`. The session follows the account plus canonical opening user turn described above, not the growing transcript. The plain `gemini` Code Assist envelope is unchanged.

**Tool schemas are adapted** to Gemini's `Schema` dialect — on this provider and on `gemini`, which
shares the adapter. `$schema`, `$id`, `$comment`,
`propertyNames`, `patternProperties`, `exclusiveMinimum`, `exclusiveMaximum`, and `const` are dropped;
every other keyword is forwarded as written. A `type` list keeps its first non-`null` entry, a `null`
in the list sets `nullable: true`, and a null-only list becomes a nullable `string`. Any schema that is
not an array — a union that settled on another member, or a plain scalar — drops `prefixItems` and any
`items` that is not a schema object, keeping an object-valued `items` as written; a typeless schema counts
as an array when it carries `prefixItems` or an array- or object-valued `items`, and otherwise loses a lone
boolean `items`. Every array is
sent with a single `items` schema: a tuple — `prefixItems`, or draft-07's array-valued `items` — is
folded into one, where identical positions keep their schema, positions that agree only on a
non-array type keep that type, and otherwise the first position's schema stands. A typed `items`
schema already sitting beside `prefixItems` is kept as written and the positions are dropped. An element whose
type lives in `anyOf`/`oneOf`/`allOf` arms is folded the same way. An array that says nothing about
its elements, or whose element schema declares no type, is sent with `items: {"type": "string"}`
unless the element implies its type through `enum` or `properties`. These fallbacks narrow the
element type rather than rejecting the request, so a tool whose tuple arrives typed as `string` is
this adaptation at work, not a routing error.

Two limits are worth knowing before you route production traffic:

- **Images must be inline.** A base64 `image` block becomes Gemini `inlineData`. A **URL image
  source is rejected with a `400`** (`URL image sources are not supported by the Gemini adapter`).
- **Tool results cannot carry rich media.** A `tool_result` whose content includes `image` or
  `document` blocks is rejected.

## Verify

```bash
shunt check    # -> config ok
shunt run
curl -sS http://127.0.0.1:3001/v1/messages \
  -H 'anthropic-version: 2023-06-01' \
  -H 'content-type: application/json' \
  -d '{"model":"claude-gemini-via-antigravity","max_tokens":16,"messages":[{"role":"user","content":"Reply with OK."}]}'
```

Confirm the response's `x-gateway-upstream` header names `antigravity`, then
[point Claude Code at shunt](/guides/connect-claude-code/).

<Aside type="note" title="Overrides">

`SHUNT_ANTIGRAVITY_AUTH_FILE` overrides the credential path; an empty value uses the default.

Native inference uses an exact canonical HTTPS root: `https://daily-cloudcode-pa.googleapis.com` or `https://cloudcode-pa.googleapis.com`. The production root is normalized to the daily control plane. Configure no path prefix, query, fragment, userinfo, or custom production port. A loopback root may stand in for a local proxy, but only its exact origin is allowed. Every inference redirect must retain the validated origin and exact SSE path/query; lookalike hosts and off-origin redirects are refused before the bearer is sent.

[`shunt login antigravity`](/reference/cli/#shunt-login-antigravity) discovers against your
**routed** Antigravity upstreams — or, before you have wired up routes, the Antigravity upstreams you
declared. A single candidate wins outright, and when several qualify the one
**named `antigravity`** wins. If several qualify and none carries that name, login refuses to guess —
it logs a warning and falls back to the default endpoint, so the project it provisions may not be
the backend your routes use. Name the upstream you want discovered `antigravity`.

</Aside>

<Aside type="caution" title="`antigravity` changed meaning">

`kind = "antigravity"` used to run the local `agy` binary. It is now the HTTP upstream, and the
subprocess transport moved to `kind = "antigravity_cli"` (built-in provider `antigravity-cli`).
A config still carrying the old meaning is refused by name rather than silently retargeted, and a
routed `antigravity` provider with no credential refuses to start:

```text
provider `antigravity` is routed but has no credential. It is now the native HTTP upstream, not the
local `agy` CLI. Run `shunt login antigravity` to authenticate it, or route to `antigravity-cli` to
stay on the deprecated subprocess transport.
```

[`shunt check`](/reference/cli/#shunt-check) runs that same guard offline, so CI catches the
misconfiguration before a rollout. The check is **presence-only** — it does not open the credential,
so an empty or stale file still passes and fails later on the request path.

</Aside>
