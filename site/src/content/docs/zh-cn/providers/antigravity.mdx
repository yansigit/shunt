内置的 **`antigravity`** 提供方通过 HTTP 在 `daily-cloudcode-pa.googleapis.com` 触达 Google 的
**Antigravity** 后端。该主机就是 Antigravity 客户端自身在发现和推理时都会访问的 `daily-` 控制平面。它讲的是与 `gemini` 提供方相同的 Code Assist 协议 ——
shunt 将 Anthropic Messages 转换为 `streamGenerateContent?alt=sse` —— 但它
用 Antigravity 订阅 token 认证,并在项目发现期间把自己标识为 `ideType: ANTIGRAVITY`。

Antigravity 还有第二种、更老的传输方式。`kind = "antigravity_cli"` 以子进程方式运行本地 `agy` 二进制,
且已**废弃** —— 见
[已废弃的 `antigravity-cli` 传输](/zh-cn/guides/providers/#已废弃的-antigravity_cli-传输)。
本页讲的是 HTTP 提供方,它完全不需要那套机制。

<Aside type="caution" title="Antigravity 的条款">

Google 的 [Antigravity 条款](https://antigravity.google/terms)直接点名了这种用法:"使用第三方软件、工具或服务访问本服务(例如将
OpenClaw 与 Antigravity OAuth 配合使用)即违反本协议",且此类违约"可能成为暂停或终止你的 Antigravity
和/或 Gemini CLI 账号的理由"。shunt 就是使用 Antigravity OAuth 的第三方软件,因此经由该提供方路由恰好落在
该条款之内。这份订阅是否值得冒这个风险由你自己决定 —— 这里没有任何东西能保护你的账号。

</Aside>

## 原生工具历史

原生 OAuth 响应使用不透明的 `call_antigravity_v2_` 工具 ID。返回工具结果时，请保留原始 ID、工具名称、参数及历史顺序。非原生 Gemini 仍支持 `call_gemini_v1_` ID，但原生 Antigravity 会拒绝这些 ID；迁移旧的原生历史时，请开始新对话。

会话标识由账户和规范化后的首条用户消息生成，因此后续请求保持同一会话。同一账户下相同的开场消息会共享会话。标签绑定账户／会话以及每次调用的上游签名、名称、参数和对话内的全局序号。这些是不使用密钥的上下文检查，而非上游来源的密码学证明：无法检测刻意重新计算的标签。上游签名按原样保留，不会伪造，也不会持久化签名缓存或签名密钥。

## 快速开始

让编码 agent 为你完成接入 —— `shunt add` 会打印一份内置的设置蓝图
(离线且只读;配置由 agent 编辑,该命令绝不会修改配置):

```bash
shunt add upstream antigravity --print | claude
```

或者按照下面的手动步骤操作。

## 1. 登录

```bash
shunt login antigravity
```

这会使用 Antigravity 自有的 OAuth 客户端运行一个 Google authorization-code 流程,并写入
`~/.shunt/antigravity-auth.json`,shunt 会读取并自动刷新它。该流程申请五个
scope:

```text
https://www.googleapis.com/auth/cloud-platform
https://www.googleapis.com/auth/userinfo.email
https://www.googleapis.com/auth/userinfo.profile
https://www.googleapis.com/auth/cclog
https://www.googleapis.com/auth/experimentsandconfigs
```

最后两个正是**Gemini CLI 的登录无法在此复用、反之亦然**的原因:一份
`~/.gemini/oauth_creds.json` token 从不携带 `cclog` 或 `experimentsandconfigs`。`google_oauth`
和 `antigravity_oauth` 不可互换。

登录还会解析你的 Code Assist 项目 —— 先 `loadCodeAssist`,再用 `onboardUser`
为首次使用的账号开通一个 —— 并把项目 id 存入凭据文件。你的第一个请求前不会再有
任何发现步骤。如果发现失败,登录仍会保存 token,并在第一个请求时重试。

## 2. 配置上游

该提供方是内置的,所以一条写着 `provider = "antigravity"` 的 `[[routes]]` 条目无需你自己的提供方表
即可工作。把它声明为有序上游则不同:**Antigravity 这些 kind 没有 `[[upstreams]]` 预设**,
因此那里不能用 `provider = "antigravity"`,你必须自己设置 `kind`、`base_url` 和 `auth`:

```toml
[[upstreams]]
name = "anthropic"
provider = "anthropic"   # 让 Anthropic 作为无路由匹配模型(例如 claude-*)的默认项

[[upstreams]]
name = "antigravity"
kind = "antigravity"
base_url = "https://daily-cloudcode-pa.googleapis.com"
auth = "antigravity_oauth"
```

有序的 `[[upstreams]]` 会替换 shunt 的内置提供方,因此显式配置还必须声明它仍然回退到的
`anthropic` 默认项(`server.default_provider` 默认为 `anthropic`)。

旧的 `[providers.antigravity]` 表形式仍然受支持 —— 但不要在同一个文件中混用 `[[upstreams]]`
和 `[providers.*]`。

## 3. 路由确切的目录模型

原生推理要求账号对应的最新 `fetchAvailableModels` 证据确认确切的 `upstream_model`。有大小上限的目录快照按后端、账号指纹和项目区分。成功缓存的快照在十分钟TTL内有效；过期快照或失败的首次查询不能授权推理。拒绝前可能进行认证和目录查询，但不支持的组合不会到达推理端点。 目录查询拒绝重定向，仅配置的端点可以提供推理准入证据。

请使用确切的Gemini目录ID。Shunt不会追加后缀、选择相近effort、重新指定消失的模型，也不会通过此原生适配器转发Claude/GPT条目。不带后缀的ID不会被扩展为另一个模型。目录可能变化；以下只是配置示例，不保证当前可用：

```toml
[[routes]]
model = "claude-gemini-via-antigravity"
provider = "antigravity"
upstream_model = "gemini-3.8-flash-high"
```

路由／提供方配置的 `effort` 优先于请求的 `output_config.effort`。显式effort必须与带后缀的目录ID一致。确切的 `-tiered` ID通过 `generationConfig.thinkingConfig.thinkingLevel` 传递 `low`、`medium` 或 `high`，未指定时默认为 `medium`。包括 `xhigh`、`max` 在内的未知值不会被静默折叠。thinking budget仍是生成控制项，不再用于猜测另一个目录模型。

## 原生传输与恢复

两种客户端模式都使用 `streamGenerateContent?alt=sse`。流式模式增量转发事件，只有非流式模式才进行有界累积。文本、推理、有序工具、用量、结束状态和内嵌错误共用一个严格解码器。畸形或截断流、不完整工具以及无效或重复结束都会报错。

仅当首次 `401` 出现在下游响应头或输出之前时，才允许同账号在内存中刷新并重放一次。项目、目录、会话、请求ID和正文保持相同，仅bearer改变。第二次 `401`、刷新失败、账号变化、发送结果不明的失败，以及响应头／输出／工具之后的错误，均不会重放或切换提供方。新恢复路径不写入凭据。现有登录／到期刷新的持久化行为不变；旧格式中由refresh-token推导的身份若变化则拒绝。取消任一种模式都会释放上游响应体和准入名额。

证据来自2026-09-07的合成数据隔离路由器／回环测试，不保证实时模型可用性。Google AI Studio Web不在支持范围内。不新增持久化签名存储、通用缓存／存储平台、跨账号项目复用或“无进展”取消启发式。

## 适配器承载的内容

适配器以 Anthropic SSE 流式传输助手的**文本**和**thinking**,并原生桥接你客户端的
**工具**:`tool_use` 变成 Gemini 的 `functionCall`,你的 `tool_result` 变成
`functionResponse`,工具声明和工具选择也随之转换。**系统提示**
变成 `systemInstruction`。Token 用量取自 Google 报告的计数 —— `promptTokenCount` 和
`candidatesTokenCount` 映射到 `input_tokens` 和 `output_tokens`。

**Thinking** 跟随请求：`thinking.type = "enabled"` 用 `budget_tokens`（默认 `1024`）设置 `thinkingConfig.thinkingBudget`，`"disabled"` 将其设为 `0`。

每个请求携带 `model`、`project`、`userAgent: "antigravity"`、`requestType: "agent"`、新的 `requestId: "agent-<uuid>"` 和 `request.sessionId`。会话基于上述账号和规范化后的首个用户轮次，而非不断增长的完整历史。普通 `gemini` Code Assist信封不变。

**工具 schema 会被调整为 Gemini 的 `Schema` 方言** —— 在本提供方以及共用同一适配器的 `gemini` 提供方上都是如此。`$schema`、`$id`、`$comment`、`propertyNames`、
`patternProperties`、`exclusiveMinimum`、`exclusiveMaximum` 和 `const` 会被丢弃,其余关键字按原样转发。`type`
列表保留其第一个非 `null` 项,列表中若有 `null` 则设置 `nullable: true`,只含 `null` 的列表则变成可为空的
`string`。任何不是数组的 schema —— 无论是落到其他成员的联合类型,还是普通标量 —— 都会丢弃
`prefixItems` 和任何不是 schema 对象的 `items`,而对象值的 `items` 原样保留;没有类型的 schema 若带有 `prefixItems`
或数组值、对象值的 `items`,则按数组处理,否则只丢弃孤立的布尔 `items`。每个数组都以单一的 `items` schema 发送:元组 —— `prefixItems`,或 draft-07 的数组值 `items` —— 会
折叠成一个,其中相同的位置保留其 schema,仅在非数组类型上一致的位置保留该类型,否则以第一个位置的 schema
为准。若 `prefixItems` 旁边已经有声明了类型的 `items` schema,则原样保留该 schema 并丢弃各位置。类型位于 `anyOf`/`oneOf`/`allOf` 分支中的元素也以同样方式折叠。对元素未作任何声明的数组,或元素
schema 未声明类型的数组,除非元素通过 `enum` 或 `properties` 暗示了类型,否则会以 `items: {"type": "string"}`
发送。这些回退只是收窄元素类型而不是拒绝请求,因此若某个工具的元组以 `string` 类型到达,那是这一调整在起作用,
而不是路由错误。

在把生产流量路由过来之前,有两项限制值得知道:

- **图像必须是内联的。** base64 的 `image` 块会变成 Gemini 的 `inlineData`。而 **URL 图像
  源会被以 `400` 拒绝**(`URL image sources are not supported by the Gemini adapter`)。
- **工具结果不能携带富媒体。** 内容中包含 `image` 或 `document` 块的 `tool_result` 会被拒绝。

## 校验

```bash
shunt check    # -> config ok
shunt run
curl -sS http://127.0.0.1:3001/v1/messages \
  -H 'anthropic-version: 2023-06-01' \
  -H 'content-type: application/json' \
  -d '{"model":"claude-gemini-via-antigravity","max_tokens":16,"messages":[{"role":"user","content":"Reply with OK."}]}'
```

确认响应的 `x-gateway-upstream` 头写的是 `antigravity`,然后
[将 Claude Code 指向 shunt](/zh-cn/guides/connect-claude-code/)。

<Aside type="note" title="覆盖项">

`SHUNT_ANTIGRAVITY_AUTH_FILE` 覆盖凭据路径，空值使用默认值。

原生推理使用确切的标准HTTPS根地址：`https://daily-cloudcode-pa.googleapis.com` 或 `https://cloudcode-pa.googleapis.com`。生产根地址会规范化为daily控制平面。不要配置路径前缀、查询、片段、用户信息或自定义生产端口。回环根地址可用于本地代理，但只允许其确切origin。每次推理重定向也必须保持已验证的origin及确切SSE路径／查询；相似主机和跨origin重定向会在发送bearer之前被拒绝。

[`shunt login antigravity`](/reference/cli/#shunt-login-antigravity) 会针对你**已路由的**
Antigravity 上游做发现 —— 或者在你还没接好路由之前,针对你所声明的 Antigravity 上游。
只有一个候选时它直接胜出,而当有多个候选合格时,**名为 `antigravity`** 的那个胜出。如果有
多个合格却都不叫这个名字,登录会拒绝猜测 —— 它记录一条警告并回退到默认端点,因此它开通的
项目可能并不是你的路由所用的那个后端。请把你希望被发现的那个上游命名为 `antigravity`。

</Aside>

<Aside type="caution" title="`antigravity` 的含义已改变">

`kind = "antigravity"` 过去运行的是本地 `agy` 二进制。现在它是 HTTP 上游,而
子进程传输迁移到了 `kind = "antigravity_cli"`(内置提供方 `antigravity-cli`)。
仍沿用旧含义的配置会按名称被拒绝,而不是被悄悄改指到别处;被路由到的
`antigravity` 提供方若没有凭据则拒绝启动:

```text
provider `antigravity` is routed but has no credential. It is now the native HTTP upstream, not the
local `agy` CLI. Run `shunt login antigravity` to authenticate it, or route to `antigravity-cli` to
stay on the deprecated subprocess transport.
```

[`shunt check`](/zh-cn/reference/cli/#shunt-check) 会离线运行同一个守卫,因此 CI 能在上线前
发现这种配置错误。该检查**只查存在性** —— 它不会打开凭据文件,
所以空的或过期的文件仍会通过,并在之后的请求路径上失败。

</Aside>
